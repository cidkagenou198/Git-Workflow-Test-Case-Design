Step 4: Undo Operation using Git (1 Mark)

In version control, situations often arise where an unintended commit is recorded. To demonstrate how to cleanly undo a commit:

  1. I made an intentional dummy commit by creating an unwanted file (unwanted_draft.txt) and committing it as 42e8318.
  2. I used git reset HEAD~1 (mixed reset) to undo the commit. This command moves the HEAD pointer back by one commit while keeping the file changes in the local working directory (untracked/unstaged), rather than abruptly discarding them.
  3. I verified the repository history using git log to confirm the commit was removed, and then deleted the unneeded file to leave a completely clean working tree.
# State before undo: Commit exists in history $ git commit -m "Draft notes for next release (accidental commit)" [main 42e8318] Draft notes for next release (accidental commit) 1 file changed, 1 insertion(+) create mode 100644 unwanted_draft.txt $ git log --oneline -n 3 42e8318 (HEAD -> main) Draft notes for next release (accidental commit) d08fcc5 Add .gitignore to exclude .log files and temp directory dd6beb4 Merge branch 'feature' into main # Executing the undo operation $ git reset HEAD~1 # State after undo: Commit removed from branch history $ git log --oneline -n 3 d08fcc5 (HEAD -> main) Add .gitignore to exclude .log files and temp directory dd6beb4 Merge branch 'feature' into main a0593d8 Add contact information section to about.html $ git status On branch main Untracked files: (use "git add <file>..." to include in what will be committed) unwanted_draft.txt nothing added to commit but untracked files present (use "git add" to track)

Question 2: Test Case Design (10 Marks)

Application Overview & Functional Requirements

The objective is to design a robust test suite for a standard User Login System comprising three interactive elements: Username input field, Password input field, and a [Login] button.

The system must strictly satisfy the following five functional requirements:

  • FR-1: Username must not be empty.
  • FR-2: Password must be at least 6 characters long.
  • FR-3: Valid username and password allow a successful login.
  • FR-4: Invalid credentials should display an appropriate error message.
  • FR-5: After 3 consecutive failed login attempts, the account should be locked.

Test Design Strategy

To ensure complete test coverage and avoid common real-world bugs, the test suite applies two core software testing techniques:

  • Equivalence Partitioning (EP): Divides inputs into valid classes (registered username, valid length password) and invalid classes (empty strings, unregistered users, mismatching passwords).
  • Boundary Value Analysis (BVA): Focuses on the minimum length boundary for passwords: testing just below the threshold (5 characters - Invalid) and exactly at the threshold (6 characters - Valid).
  • State Transition & Security Testing: Validates consecutive authentication failure counters to ensure account lockout triggers precisely on the 3rd consecutive failed attempt, and that a successful login resets the failure counter.
